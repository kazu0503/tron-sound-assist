# 評価結果

## 評価の方針

**この作品にとって最も重要な指標は「誤報を出さないこと」です。**
危険音でないものを危険と誤って伝え続ける機器は、使う人に無視されるようになり、
本当に危険なときにも気づいてもらえなくなるためです。
そのため正解率だけでなく、**「その他」クラスの取りこぼし（＝誤報）** を重点的に見ます。

### データ分割（リーク防止）

1秒窓に切ったデータをランダムに分割すると、**同じ録音から切り出した窓が学習側と
テスト側の両方に入り**、実力より高い数値が出てしまいます。
これを避けるため、**ファイル（録音クリップ）単位で fold を割り当て**、
fold をまたいで窓が分かれないようにしています。

ただし実機録音には、同じ再生元の音をスマートフォンで何回か鳴らして録ったファイルが含まれます。
再生元の音ごとには分けていないため、評価が実力よりやや高めに出ている可能性があります。

fold1〜5 を順にテストにして5回学習する5分割交差検証で評価しました。
実機録音データはすべて fold1〜5 に割り当てているので、91窓すべてを一度ずつテストしています。

## 1. 実機録音データでの性能（最重要）

micro:bit の内蔵マイクで実際に録音した 91窓（67ファイル）の評価です。
**実際に使われる条件そのもの**なので、この作品にとって一番意味のある数値です。

> 2026年9月27日、学習に使っていた効果音素材の1点が、配布サイトの利用規約でAIの学習への使用を
> 禁止されていることが分かったため、その素材を除いて学習し直しました（[../CREDITS.md](../CREDITS.md)）。
> 以下は、学習し直した後のデータでの結果です。

**正解率 86.8 %**（n=91）

| クラス | 適合率 | 再現率 | F1 | 件数 |
|---|---|---|---|---|
| サイレン | **1.000** | 0.852 | 0.920 | 27 |
| クラクション | 0.786 | 0.647 | 0.710 | 17 |
| その他 | 0.833 | 0.957 | 0.891 | 47 |

**混同行列**（行＝正解、列＝予測。いちばん確率の高いクラスを予測とした場合）

|  | サイレン | クラクション | その他 |
|---|---|---|---|
| **サイレン** | **23** | 1 | 3 |
| **クラクション** | 0 | **11** | 6 |
| **その他** | 0 | 2 | **45** |

### 学習のたびの結果のばらつき

ニューラルネットの学習は、初期値などの乱数によって毎回少しずつ結果が変わります。
同じ条件で5分割交差検証をもう一度行うと、実機録音の正解率は **84.6 %**、
「その他」をクラクションと判定した窓は5窓でした。
また、素材を除く前のデータで同じ評価をやり直すと 85.7 % で、除いたことによる大きな差は見られませんでした。
以前この資料に載せていた 90.1 %（誤判定0窓）は、1回の学習での結果で、やや良いほうに出た値でした。

### ここから読み取れること

**① 通知の条件を満たす窓は0窓でした。**
「その他」47窓のうち2窓は、いちばん確率の高いクラスがクラクションでした。
実機の通知の条件（[ARCHITECTURE.md](ARCHITECTURE.md)）は、どの場合も、通知するその窓の確信度が60%以上であることが必要です。
「その他」47窓で、サイレンかクラクションの確率が60%以上になった窓は **0窓**（最大56.7%）でした。
そのため、前後の判定がどう続いても、この47窓から通知は出ません。
ただし「その他」の録音は1秒ずつの短いもので、長く続く生活音を連続して聞かせた評価ではありません。

**② サイレンの適合率が 1.000 です。**
「サイレンだ」と判定したときは、**すべて本当にサイレン**でした。

**③ 弱点はクラクションの取りこぼしです。**
クラクション17窓のうち6窓を「その他」と判定しました（再現率 0.647）。
原因は後述します（[5. 既知の弱点](#5-既知の弱点)）。

> 「取りこぼす」方向の誤りが多く、「鳴っていないのに鳴ったと言う」誤りは少ない傾向です。

## 3. レベル不変性の検証

**この作品の技術的な核心部分の検証です。**

開発当初は固定ゲインで int16 を float に変換していましたが、
マイクのゲインや音源との距離が変わると対数メルの分布ごとズレてしまい、
**実機でサイレンをクラクションと誤判定する**問題が起きていました。

対策として、特徴量を計算する前に **1秒窓ごとに DC を除去し RMS を基準値に揃える**
処理を、学習側（Python）と実機側（C）の両方に入れました。

### 検証：同じ音を音量だけ変えて入力する

`src/validate_rms.py` による実測。実機録音のサイレンを入力し、振幅を変えて比較しました。

| 振幅 | 出力（siren, car_horn, other） | ×0.1 のときとの最大差 |
|---|---|---|
| ×0.1 | 0.9991807, 0.0000000655, 0.0008192 | 0.000e+00 |
| ×0.5 | 0.9991807, 0.0000000655, 0.0008192 | 1.979e-09 |
| ×1.0 | 0.9991807, 0.0000000655, 0.0008192 | 1.979e-09 |
| ×2.0 | 0.9991807, 0.0000000655, 0.0008192 | 1.979e-09 |
| ×10.0 | 0.9991807, 0.0000000655, 0.0008192 | 1.979e-09 |

**同じ録音の振幅を100倍の幅で変えても、出力確率がほぼ一致します。**

これにより、
- マイクゲインの手動較正が**原理的に不要**になりました
- 音源との距離やマイクの感度が変わっても、判定がぶれにくくなりました
- 個体差や設置条件が変わっても再調整が要りません

> ただし、ここで確かめたのは「同じ録音の音量だけを変えた場合」です。
> 実際に小さな音を聞かせると、周りの雑音との比が小さくなるため反応しにくくなります（[5. 既知の弱点](#5-既知の弱点)）。

## 4. Python 実装と C 実装の数値一致

学習は Python（Keras）、実機は手書きの C 実装です。
**両者が同じ答えを出さなければ、学習した性能は実機で再現されません。**

実機録音を入力し、Python と C の出力確率を突き合わせました（学習し直した後のモデル）。

| 入力 | 最大絶対誤差 |
|---|---|
| サイレン録音 | 1.164e-09 |
| クラクション録音 | 5.962e-08 |
| 環境音録音 | 5.960e-07 |

**最大誤差 5.96e-7。** float 演算の丸め誤差の範囲内であり、両実装は一致しています。
検証対象は、特徴量抽出（FFT・メルフィルタバンク・対数）と CNN 推論の**全経路**です。
再現手順は [BUILD.md](BUILD.md) の「5. 学習をやり直す場合」を参照してください。

## 5. 既知の弱点

### 短いクラクションを取りこぼすことがある

実機データでクラクションの再現率が 0.647 に留まっています。原因は2つあります。

**① CNN が時間方向に平均を取っている**

モデルの最終段は GlobalAveragePooling で、1秒窓の30フレーム全体を平均します。
そのため 0.3秒しか鳴らない音は **1/3 に薄められて**しまいます。
長いクラクション（1秒以上）は確信度990超で検出できるのに対し、
短い「プッ」という音は反応が弱くなります。

**② スマートフォンのスピーカーで再生した音で学習・検証している**

クラクションの基本波は 400〜500Hz ですが、小型スピーカーは低音を十分に再生できません。
実機録音データでは 2,400〜3,500Hz の高調波が支配的なものが多く、
実物のクラクションとは特性が異なる可能性があります。

### 実機での通知テスト（音の長さ別）

腕に着けた完成品で、スマートフォンから短いクラクション音を再生して確かめました。
通知条件（確信度700以上なら1回で通知）を入れた、**学習し直す前の版（9月26日に発送した本体）**での結果です。学習し直した v2 は、本体を発送した後に作ったため、実機ではまだ試せていません。

| 音が鳴っている長さ | 通知された回数 |
|---|---|
| 約0.7秒 | **10回中10回** |
| 約0.3秒 | 10回中2回 |
| 約0.1秒 | 通知されない |
| 話し声・拍手・物音（5分間） | **誤報 0回** |

約0.3秒の音は、1秒の判定窓の**境目にまたがるかどうか**で結果が変わります。
窓の中に収まると通知され、2つの窓に分かれると薄まって通知されません。

### 改善の方向

- **窓を 0.5 秒ずつ重ねる**（推論約350ms、1秒の予算に対し余裕があるため追加メモリ無しで実装可能）
- GlobalAveragePooling に最大値プーリングを併用し、短い事象への応答性を上げる
- 実物のクラクションを屋外で録音して学習データに加える

### 小さな音には反応しにくい

実機で試すと、**大きめの音でないと反応しない**ことが分かっています。

RMS正規化は音の大きさをそろえますが、周りの雑音も一緒に大きくします。
聞かせた音が小さいと、1秒の中で雑音の占める割合が大きくなり、
特徴量が「その他」に近づいてしまいます。音量そのものではなく、**周りの雑音との比（SNR）**で決まる弱点です。

改善の方向：

- 屋外で遠くのサイレンなど、小さな音を録音して学習データに加える
- 学習時に混ぜる雑音の比率を、より厳しい条件（SNRの低い側）まで広げる
- SAADC のゲインを上げて、マイクからの信号を大きく取り込む

### 静音時の単発誤判定

RMS正規化は静かな部屋のノイズも基準レベルまで増幅するため、
稀に単発で「クラクションらしい」と判定されることがあります。

これに対しては通知側で対策しています（[ARCHITECTURE.md](ARCHITECTURE.md) 参照）。

- サイレン：**2回続けて**サイレンと判定され、そのときの確信度が 600/1000 以上
- クラクション：確信度 **700/1000 以上なら1回**（短い音のため）

のときだけ発報するため、**確信度が 700/1000 未満の単発の誤判定では通知されません。**
上記の実機テストでも誤報は観測されていません。

## 6. 実機での動作性能

micro:bit v2（nRF52833 / Cortex-M4F 64MHz / RAM 128KB / Flash 512KB）での実測値です。

| 項目 | 実測値 | 備考 |
|---|---|---|
| 推論時間 | **約350 ms** | 1秒窓あたり。特徴量抽出＋CNN推論の合計（実測340〜380ms） |
| CPU使用率 | **34 %** | 残り66%で録音・通知・待機 |
| RAM (bss) | **104,516 B** (102 KB) | 128KB中。うち録音バッファ32KB |
| Flash (text) | **86,652 B** (85 KB) | 512KB中 |
| モデルパラメータ | 7,043 個 | float32 で約28KB |
| 特徴量次元 | 960 | 32メル帯域 × 30フレーム |
| サンプリング | 8 kHz / 12 bit | SAADC + EasyDMA |

推論に1秒の予算のうち約350msしか使っていないため、
**録音を一切止めずに**リアルタイム処理できています。

> 推論時間は実機のシリアル出力で毎回計測して表示しています
> （`=> SIREN conf=882 (340ms) run=2`）。特別な測定器は不要です。
