# アーキテクチャ解説

## 1. 全体像

| 内蔵マイク | → | SAADC＋EasyDMA | → | 特徴量抽出 | → | CNN | → | 通知 |
|---|---|---|---|---|---|---|---|---|
| アナログ出力<br>P0.05 / AIN3 | | 8kHz・12bit | | 対数メル<br>32×30 | | 7,043パラメータ<br>3クラス | | LED＋振動 |

すべて micro:bit 単体（nRF52833 / Cortex-M4F 64MHz）で完結し、外部との通信は行いません。

---

## 2. タスク構成（μT-Kernel 3.0）

| タスク | 優先度 | 役割 | 待ち方 |
|---|---|---|---|
| （初期タスク） | 1 | タスク生成後は `tk_slp_tsk(TMO_FEVR)` で永久に眠る | — |
| **T_audio** | 2 | SAADC ピンポンバッファ駆動、録音完了通知 | `tk_dly_tsk(2)` でポーリング |
| **T_notify** | 3 | 後処理・LED・振動モーター制御 | `tk_rcv_mbf` 100ms待ち |
| **T_infer** | 4 | 特徴量抽出＋CNN推論 | `tk_wai_flg` 無限待ち |

### なぜこの優先度なのか

**一番重い処理（推論）を一番低い優先度に置いています。** 一見逆に思えますが、これが正解です。

- 推論は約350msかかりますが、**遅れても構いません**（次の1秒までに終わればよい）
- 録音は **1サンプルでも落としたら取り返せません**

そこで T_audio を最優先にし、普段は `tk_dly_tsk` で眠って CPU を T_infer に明け渡し、
DMA が1秒ぶんを埋めた瞬間だけ起きてバッファを切り替えます。
推論中でも T_audio が確実に割り込めるため、**CPUの約35%を推論に使いながら、推論中も録音を続けられます**（面を切り替えるときにできる空白は最大約2ms）。

### タスク間通信

```
T_audio ──tk_set_flg(FLG_FILLED)──▶ T_infer ──tk_snd_mbf(RESULT)──▶ T_notify
         イベントフラグ                        メッセージバッファ
```

- **イベントフラグ**：「片面が埋まった」という事象だけを伝えればよいので軽量なフラグを使用
- **メッセージバッファ**：判定クラス・確信度・推論時間を構造体で渡すためデータ転送が必要。
  送信は `TMO_POL`（待たない）にしてあり、T_notify が詰まっても T_infer は止まりません

## 3. 録音：ピンポンバッファで推論中も録音を続ける

nRF52833 の SAADC は EasyDMA を持ち、変換結果を直接メモリに書き込めます。
ただし1回の転送が終わる（`EVENTS_END`）と停止してしまうため、素直に書くと
「停止 → 次の転送を設定 → 再開」の間が**録音の空白**になります。

そこで **RESULT.PTR がダブルバッファになっている**性質を使います。

```c
short buf[2][8000];          /* 1秒ぶん × 2面 */

/* 起動時 */
RESULT.PTR = buf[0];  TASKS_START;
EVENTS_STARTED を待つ → RESULT.PTR = buf[1];   /* 次の面を"予約" */
TASKS_SAMPLE;                                   /* 内蔵タイマで8kHz連続サンプリング */

/* 定常ループ */
EVENTS_END を待つ            /* buf[0] が埋まった */
  → TASKS_START              /* 予約済みの buf[1] へ即座に継続（ここが肝） */
  → tk_set_flg()             /* 埋まった buf[0] を T_infer へ渡す */
  → EVENTS_STARTED を待つ → RESULT.PTR = buf[0];  /* さらに次を予約 */
```

`EVENTS_END` の直後に `TASKS_START` を撃つだけで次の面へ移れるので、
バッファを設定し直す待ち時間がいりません。
ただし T_audio は `EVENTS_END` を2ms周期で確認しているため、
面を切り替えるときに**最大約2msの空白**ができます（1秒あたり最大0.2%）。

T_infer が buf[0] を処理している間、DMA は buf[1] を埋めています。
処理は約350ms（実測340〜380ms）、DMAは1000msかかるので追い越されることはありません。

## 4. 信号処理

### 4.1 マイクとADC

micro:bit v2 の内蔵マイクは **アナログ出力の MEMS マイク**（Knowles SPU0410LR5H）です。
PDM マイクではないため、nRF52833 の PDM ペリフェラルではなく **SAADC** で取り込みます。

| 項目 | 設定 |
|---|---|
| 信号ピン | P0.05（AIN3） |
| 電源イネーブル | P0.20（HIGH でマイクON。基板のマイクLEDも点灯する） |
| 分解能 | 12bit |
| ゲイン | ×2（`CH0.CONFIG` GAIN=6） |
| 取得時間 | 40µs（`CH0.CONFIG` TACQ=5） |
| サンプリング | 内蔵タイマ 8kHz（`SAMPLERATE` = (1<<12) \| 2000） |

> キット付属のサンプルに ADC／マイクの作例が無かったため、**このドライバは自作しています。**
> 学習データ収集用の録音アプリと推論アプリで **同じ SAADC 設定を使うこと**が重要です。
> 設定が違うと、学習したデータと実機で聞こえる音の特性がずれて精度が落ちます。

### 4.2 特徴量

```
1秒窓 (8000サンプル int16)
  → DC除去（平均を引く）
  → RMS正規化（RMSを 0.1 に揃える）          ★レベル不変化
  → フレーム分割（長さ512 / ホップ256 / センタリングなし → 30フレーム）
  → Hann窓（periodic）
  → FFT 512点 → パワースペクトル（257ビン）
  → メルフィルタバンク 32帯域（HTK式 mel = 2595·log10(1+f/700), 0〜4000Hz）
  → log(mel + 1e-10)
  → 32 × 30 = 960次元
  → 標準化（学習時の平均・標準偏差）
```

**RMS正規化がこの作品の要点です。** 詳細は [EVALUATION.md](EVALUATION.md) の
「レベル不変性の検証」を参照してください。

実装上は、正規化のために別バッファを作ると 32KB 必要になってしまうため、
**スケール係数を窓関数に畳み込む**ことでメモリを使わずに実現しています。

```c
re[i] = (raw[t*HOP + i] - dc) * k * window[i];   /* k = RMS_TARGET / rms */
```

### 4.3 CNN

```
入力 32×30×1
  Conv2D(8, 3×3, relu) → MaxPool
  Conv2D(16, 3×3, relu) → MaxPool
  Conv2D(32, 3×3, relu)
  GlobalAveragePooling
  Dense(32, relu) → Dropout(0.3)
  Dense(3, softmax)
```

パラメータ 7,043 個（float32 で約28KB）。Keras で学習し、
重みを C の配列（`cnn_weights.h`）として書き出して**手書きのC実装で推論**します。

推論ライブラリに依存しないため、μT-Kernel アプリに素直に組み込めます。
また Python と C の出力が一致することを PC 上で検証できます（誤差 5.96e-7）。

## 5. 通知の後処理

推論は1秒ごとに結果を出しますが、**そのまま通知すると単発の誤判定で誤報**が出ます。
RMS正規化により静かな部屋のノイズも増幅されるため、稀に「クラクションらしい」と
判定されることがあるためです。

そこで T_notify で次の条件を両方満たしたときだけ発報します。

| 条件 | 値 | 理由 |
|---|---|---|
| サイレン | **2回続けて**サイレンと判定され、そのときの確信度が 600/1000 以上 | 鳴り続ける音なので、慎重に判定しても遅れない。単発の誤判定を弾く |
| クラクション | 確信度 **700/1000 以上なら1回で**（または2回続けてクラクションと判定され、そのときの確信度が600以上） | 1秒以内に鳴り終わる短い音で、2回連続の判定がほとんど起きないため |
| 保持時間 | 3秒 | 通知がちらつかないようにする |

当初は両方とも「2回連続」にしていましたが、実機でクラクションを鳴らすと
1回しか判定されず（判定自体は確信度98.7%と正しい）、通知されませんでした。
そこで音の種類ごとに条件を分けました。当初は1回条件を85%以上にしていましたが、
0.3秒ほどの短いクラクションが「クラクション・確信度78%」と正しく判定されても通知されない例があったため、
**70%以上に下げました**。下げた後も、5分間の話し声・拍手・物音で誤報は出ていません（[EVALUATION.md](EVALUATION.md) 参照）。

## 6. ファイル構成

### 実機側（`firmware/`）

| ファイル | 内容 |
|---|---|
| `app_main.c` | 3タスクの生成と各タスクの処理、SAADC制御、LED/振動制御 |
| `infer_mb.c` | 特徴量抽出（FFT・メル）とCNN推論。float最適化済み |
| `infer_mb.h` | 推論API |
| `cnn_weights.h` | 学習済み重み（`export_cnn_weights.py` が自動生成） |
| `app_main_record.c` | 学習データ収集用の録音アプリ（推論はしない） |

`infer_mb.c` は micro:bit の RAM 128KB に収めるため次の工夫をしています。

- 全計算を float に統一（double はM4で soft-float になり遅い／メモリも倍）
- メルフィルタバンクを疎行列として保持（32×257 の密行列 64KB → 数KB）
- CNN の中間バッファを2枚で使い回す

### PC側（`src/`, `c_impl/`, `tools/`）

| ファイル | 内容 |
|---|---|
| `src/config.py` | 特徴量パラメータの一元管理（C側と必ず一致させる） |
| `src/features_ref.py` | 組み込み版特徴量の Python 参照実装＋RMS正規化 |
| `src/ingest_device.py` | 実機録音を1秒窓に切って読み込む（ファイル単位fold割当） |
| `src/train_device.py` | 学習本体（公開データ＋実機録音） |
| `src/export_cnn_weights.py` | 重みを `cnn_weights.h` へ書き出す |
| `src/validate_rms.py` | Python↔C の一致とレベル不変性を検証 |
| `src/eval_cv.py` | 5分割交差検証（評価資料用） |
| `c_impl/infer_mb.c` | 実機と同一の推論コード（PC上で検証するため） |
| `tools/record_serial.py` | シリアル経由で実機録音を WAV 保存 |
| `tools/check_window.py` | 録音の品質判定（1秒窓ごとのピーク突出量） |

## 7. 開発時に踏んだ落とし穴

作品を再現・改造する方への注意点です。

| 事象 | 原因と対策 |
|---|---|
| 起動直後に `SYSTEM SHUTDOWN` する | `usermain()` が return するとカーネルが停止する仕様。タスク生成後は `tk_slp_tsk(TMO_FEVR)` で眠らせる |
| ビルドが通らない／文字化けする | 展開先パスに日本語やスペースを含めない |
| LEDを触ったら動作が不安定になる | `P0.00` は 32.768kHz 水晶の入力。LED列として使わないこと |
| 振動モーターを繋いだらマイコンが壊れた | GPIO直結は不可（1本5mAまで）。ドライバ内蔵モジュールを使う |
| 実機だけ判定がおかしい | 録音時と推論時で SAADC の設定（ゲイン・取得時間）を必ず揃える |
| リンクエラー `multiple definition of usermain` | `app_sample/*.c` は全部ビルドされる。`usermain()` を持つファイルは1つだけにする |
